# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Что это за проект

**AIda** — Telegram-бот, который превращает материалы преподавателя в тренажёр
для его учеников. Преподаватель загружает свои билеты в .docx, бот их разбирает
и собирает тренажёр; ученик приходит по приглашению и занимается на материалах
именно своего преподавателя.

Сделан на базе бота по истории Беларуси: каркас aiogram, RAG, движок тестов
и карточек переиспользованы. История осталась рабочим предметом и источником
базового контента.

Планы работ: `PLAN.md` (прототип по дням), `ROADMAP.md` (полная версия, подписка).

## Запуск и проверки

Локально проект работает в виртуальном окружении на **Python 3.12**
(на системном 3.14 нет готовых пакетов для FAISS):

```bash
.venv/Scripts/python.exe -m bot.main      # запуск бота
.venv/Scripts/python.exe -m pytest -q     # тесты
```

**Вывод в консоль Windows ломается на кириллице** (cp1251). Для любых команд
с русским выводом:

```bash
PYTHONIOENCODING=utf-8 ./.venv/Scripts/python.exe ...
```

На сервере (Linux, systemd) — юнит `historybot`, при переезде на AIda
переименовать:

```bash
sudo systemctl restart historybot
sudo journalctl -u historybot -f
```

Админские команды в Telegram: `/update` (перечитать Google Sheets),
`/reindex` (пересобрать FAISS), `/reparse` (перегнать все загруженные
преподавателями .docx текущей версией парсера), `/grant` (выдать доступ
по номеру телефона), `/requests` (заявки на продление, разбор по карточкам),
`/base_reports` (общие вопросы, скрытые по жалобам, — вернуть или убрать),
`/subs` (кто есть кто и что выдано впрок), `/sub_test` (репетиция состояний
подписки на себе).

## Архитектура

### Два уровня

**Предмет** задаёт «как работает»: какие режимы включены и откуда берётся
контент. Настраивается в `subjects.py`, в коде. Преподаватель это не трогает.

**Преподаватель** задаёт «на чём работает»: его билеты. Изоляция идёт по
`teacher_id` через пути на диске, а не через отдельных ботов или базы.

### Раскладка контента

Формат файлов одинаковый в обоих слоях, поэтому код читает контент по пути
и не знает, чей он:

```
data/
  subjects/{subject}/          базовый слой, общий для всех
      sheets_cache.json        снимок общих тестов и карточек
      theory_cache.json        теория по темам
  teachers/{tg_id}/{subject}/  контент преподавателя
      uploads/                 оригиналы .docx без картинок
      tests.json               результат разбора
      manifest.json            что, когда, сколько, версия парсера
  vectorstore/                 общий FAISS-индекс по учебнику истории
```

Пути строит `services/storage.py` — не собирать их вручную в хендлерах.

### Кто какой контент видит

`services/content_provider.py` — **единственное** место, где решается этот
вопрос. Хендлеры запрашивают набор по `telegram_id` и не знают о слоях.
Политика берётся из `SUBJECTS[subject]["sources"]`:

| Режим | Политика | Куда растёт |
|---|---|---|
| tests | `teacher` | teacher + добор из базы |
| flashcards | `base` | base + teacher |
| ask | `base` | base + teacher |

Включить смешивание — правка конфига, не переписывание режимов.

**Ключевой инвариант: ученик видит вопросы только своего преподавателя.**
Ломать нельзя, покрыто тестами в `tests/test_content_provider.py`.

Преподаватель получает собственный контент (`resolve_teacher_id` возвращает
его самого) — поэтому режим «пройти свой тренажёр» работает без отдельной
ветки кода.

### Данные при старте

`bot/main.py` → `.env` → `init_db()` → снимок Sheets с диска (если есть —
в Google не ходим) → теория с диска → FAISS-индекс (если папка на месте,
пересборка пропускается) → роутеры → polling.

## Роли и онбординг

`/start` → выбор роли → выбор предмета → дальше по-разному:

- **преподаватель**: сразу создаются папки и код приглашения, анкету не спрашиваем;
- **ученик**: имя и класс, привязка к преподавателю по коду.

Схема БД (`database/db.py`, SQLite): `users` (роль, `teacher_id`,
`current_subject`), `teachers` (код приглашения), `teacher_content`,
`mistakes`, `completed_topics`, `subscriptions` (доступ преподавателя),
`pending_grants` (оплата на номер, которого в базе ещё нет).

**Состояние бота тоже на диске** — `database/fsm_storage.py`, таблица
`fsm_sessions`. Раньше стоял `MemoryStorage`, и любой перезапуск обрывал
всем незаконченные тесты молча. Redis не берём: база уже есть, а нагрузка
здесь — одна запись на нажатие. Брошенные сессии чистятся при старте,
срок жизни `SESSION_TTL_HOURS = 48`.

В aiosqlite соединение нельзя сначала `await`, а потом открывать через
`async with` — второе ожидание не возвращается, и бот виснет намертво.
Поэтому `_open()` отдаёт менеджер контекста, а не готовое соединение.

**Миграций нет** — только `CREATE TABLE IF NOT EXISTS`. При изменении схемы
на живой базе это надо решать отдельно.

## Подписка и доступ

`services/subscription.py` — **единственное место, где решается, работает
бот у человека или нет.** Хендлеры спрашивают `access_for_user` и ничего
не знают ни про пробный период, ни про даты.

**Подписка на человека, а не на предмет.** Преподаватель в базе — это пара
«человек + предмет», но платит он один раз: расходы зависят от числа
учеников, а ученик по русскому стоит столько же, сколько по истории.
Таблица `subscriptions` — одна строка на `tg_user_id`.

**Пробный период — месяц** (`TRIAL_DAYS`), заводится при регистрации
преподавателя, лимит на это время — как на минимальном тарифе
(`TRIAL_STUDENT_LIMIT = 10`). По истечении бот замолкает целиком: и на
материалах преподавателя, и на общих. Вечного бесплатного тарифа нет
сознательно — он не создаёт момента оплаты никогда.

**Кто завёлся в боте до 10.09.2026 — получает четыре месяца, а не месяц**
(`GRANDFATHER_BEFORE`, `GRANDFATHER_MONTHS`). Срок им меняем мы, а не они,
и упираться в стену через месяц из-за нашей правки они не должны. Сравнение
идёт с `users.created_at`, поэтому правило сработает и для того, кто зайдёт
впервые через полгода — запускать ничего руками не нужно, в том числе
на сервере.

**Ученик подписки не имеет**: его занятия держатся на доступе преподавателя.
Когда доступ кончился, ученику говорится «занятия временно недоступны» —
честное «преподаватель не продлил» подставляет преподавателя перед его же
клиентом. Давить надо уведомлением самому преподавателю.

**Проверка стоит заслонкой на входе** (`bot/access.py`,
`SubscriptionMiddleware` на `dp.message` и `dp.callback_query`), а не
в каждом режиме: точек входа много — кнопка, инлайн-кнопка, команда, старое
сообщение из истории чата, — и расставлять проверку по ним всем значит
оставить дырку. Новый режим закрывается сам собой.

Сквозь заслонку всегда проходят: команды, экран «💳 Подписка», колбэки
`sub:` и присланный контакт. Иначе доступ было бы нечем продлить.

**Ключ выдачи — номер телефона**, а не Telegram ID: по номеру человек
опознаётся во внешней кассе, и его же телеграм отдаёт подтверждённым
(кнопка `request_contact`). Ручная выдача — `/grant <номер> <месяцы>
[лимит]`. **Незнакомый номер — не отказ:** выдача ложится в `pending_grants`
и применяется сама, когда преподаватель поделится этим номером. Так
оплативший до первого захода в бота получает доступ без нашего участия.

Продление считается **от более поздней из дат** (`_extend`): оплата
в середине пробного периода не съедает его остаток.

**Лимит учеников жёсткий** (`student_slot`): одиннадцатый по коду
не подключится, иначе тариф по числу учеников ничего не значит. Ученику
причину не называют, преподавателю уходит уведомление. Уже подключённых
это не касается — они не «новые».

**Продление — три шага в боте:** тариф → срок → заявка. Цены и ступени
лежат в `TARIFFS` и `TERMS` (вариант Б из `ЭКОНОМИКА.md`, выбран 10.09.2026),
считаются в одном месте и правятся там же. Валюта — `CURRENCY = "BYN"`:
«руб» в Беларуси читается и как российские рубли, а разница тридцатикратная.
Скидка за срок — ровная лестница 0 / 10 / 20 / 30 на 1 / 3 / 6 / 12 месяцев;
**месяц без скидки намеренно самый невыгодный**: он нужен как низкий вход,
но не должен быть дырой, в которой остаются навсегда. Выбор едет в самих кнопках
(`sub:ren:term:30:6`), а не в состоянии на сервере: перезапуск посреди
выбора ничего не рвёт.

Реквизитов в боте нет сознательно — **заявка падает админу в этот же бот**
(`renewal_requests` плюс сообщение с кнопкой «Выдать доступ», которая делает
то же, что `/grant`). Сообщение тонет в переписке, поэтому есть и постоянный
экран — **`/requests`, разбор по одной карточке** с листалкой, как у спорных
вопросов. Заявка уходит из списка только двумя способами: выдачей доступа
или кнопкой «Закрыть без выдачи» — договорились иначе, человек передумал.
Новая заявка **заменяет** прежние открытые от того же человека: иначе трижды
нажатая кнопка даёт три одинаковые карточки, и непонятно, о чём в итоге
договаривались. Выдача заменяет карточку распиской на месте — по ней нельзя
нажать «выдать» второй раз. Дальше человек связывается лично. Когда появится
GetCourse, меняется только последний шаг. **Заявку нельзя отправить без
номера телефона** — иначе оплату не к чему привязать; это же заставляет
номера появляться без уговоров.

Имя и `@username` из телеграма пишутся при каждом действии
(`ActivityMiddleware` → `update_last_active`) в колонки `users.username`
и `users.tg_name`. Анкетное имя ученика (`name`) ими не подменяется —
его он вводил сам. Без этого в заявке и в `/subs` вместо человека стоял бы
«ID 481234567», а написать ему было бы нечем.

**Репетиция состояний — `/sub_test`** (админская). Переключает собственную
подписку между «пробный 30 дней», «пробный 2 дня», «кончился» и «оплачено
6 месяцев» и снимает с админа обход заслонки (`GUARD_ON_ADMINS`, только
в памяти — перезапуск возвращает обход). Без неё увидеть блокировку своими
глазами нельзя: админов заслонка не проверяет. Колбэки идут с префиксом
`sub:` осознанно — заслонка его пропускает, иначе из состояния «доступ
кончился» кнопками нельзя было бы вернуться.

Кнопка «поделиться номером» бывает **только на нижней клавиатуре** —
инлайновой такой в телеграме нет. Поэтому она на один запрос подменяет
клавиатуру кабинета, и кабинет возвращается сразу после ответа, в том числе
после отмены. Это единственное осознанное исключение из правила «не
пересылать клавиатуру там, где режим не меняется».

## Загрузка билетов преподавателем

`bot/handlers/teacher_upload.py` → `services/teacher_content.py`.

1. Приём `.docx` и PDF (лимит 20 МБ — больше Telegram боту не отдаёт).
2. `services/docx_tools.py:strip_media` — картинки заменяются заглушкой 1×1.
   В реальных билетах это 94% веса, а парсеру они не нужны. Связи внутри
   документа остаются целыми, разбор после чистки идентичен.
3. Оригинал кладётся в `uploads/` и **никогда не удаляется** — чтобы новую
   версию парсера можно было прогнать по всему накопленному без просьб
   к преподавателям перезаливать.
4. `tests.json` **всегда пересобирается из `uploads/` целиком**, а не
   дописывается. Поэтому повторная загрузка файла с тем же именем заменяет
   его вопросы, а не двоит.

## Разделы преподавателя

Сетка разделов программы живёт в `subjects.py` (`SUBJECTS[subject]["sections"]`)
— ключи те же, что в поле `Раздел` базового контента, поэтому вопросы
преподавателя и общие лежат в одной системе координат. Свои разделы
преподаватель добавляет сам, они получают ключи `c1`, `c2` и хранятся
в его манифесте.

**Раздел привязан к файлу целиком, а не к отдельному вопросу.** Привязка
лежит в `manifest.json` (`files[].section`), а не в строках `tests.json`:
строки пересобираются из `uploads/` при каждой загрузке и при `/reparse`,
и раскладка бы стиралась. `rebuild()` читает прежний манифест и подставляет
раздел в строки заново — покрыто `tests/test_sections.py`.

Логика без диска и бота — `services/sections.py`: список разделов, названия
и подсказка по имени файла (годы, римские века, ключевые слова). При ничьей
подсказка молчит: подтверждённая не глядя, она портит материалы тише,
чем лишний вопрос.

Порядок на экране: файл можно прислать в любой момент, бот разбирает его
и спрашивает раздел; выбранный раздел держится до конца сессии, поэтому
пачку файлов не переспрашивают. Кнопка кабинета ведёт в мастер «сначала
раздел, потом файл». Старые загрузки разбираются из «Мой тренажёр» →
«Разделы» → «Разложить».

**У ученика** список разделов строится из его собственного набора вопросов
(`_available_sections` в `bot/handlers/tests.py`): показываются только
непустые разделы, включая свои разделы преподавателя. Вопросы без раздела
собраны в псевдораздел **«🔀 Смешанные вопросы»** — это полные билеты, где
разделы перемешаны: приписать им один нельзя, а тренироваться на них нужно.
Ключ псевдораздела — `UNSORTED_KEY`, внутри превращается в пустой ключ.

**Преподаватель должен понимать, где ученик найдёт загруженное** (17.09.2026:
трое подряд загрузили вопросы и не нашли их, хотя показ работал). Отсюда:

- рядом с разделом и темой — число вопросов (`with_count`). Подпись
  раздела короткая (`Section.label`): полное название на телефоне
  обрезалось вместе с числом, оно стоит в заголовке следующего экрана
  (`_section_heading` — там же свой раздел называется по имени, а не «c1»);
- отчёт о загрузке называет путь ученика (`teacher_upload.student_path`)
  теми же подписями, что на кнопках (`BTN_BY_SECTION`), и предупреждает,
  если стоят «только общие материалы», — с кнопкой переключения;
- **сам преподаватель в режиме ученика видит и свои пустые разделы и темы**
  с пометкой «пока пусто» (`_own_places`, `owner=`), ученику они
  по-прежнему не показываются;
- **выбранный раздел держится `STICKY_MINUTES` = 30 минут** (`section_at`),
  а не до конца сессии: состояние бота хранится на диске двое суток, и файл,
  присланный назавтра, молча ложился во вчерашний раздел. Если бот ждёт файл
  после выбора места — место действует без срока;
- **файл с тем же именем в другое место не переносится молча**: он
  обновляется на прежнем месте, и бот спрашивает «перенести?» (`upl:move`,
  `upl:keep`). Имя известно до сохранения — `teacher_content.upload_name`.

Название одно на обе стороны (`sections.UNSORTED_TITLE`): преподаватель
кладёт файл в «Смешанные вопросы» и там же его находит ученик. Название
говорит о составе, а не о происхождении файла: «Пока без раздела» читалось
как «решу потом», «Готовые варианты» — как источник, а важно ровно то,
что внутри вопросы из разных разделов.

## Темы — второй уровень под разделами

Ключ темы **начинается с ключа раздела**: `6_1` лежит в разделе `6`, своя тема
преподавателя там же — `6_c1`. Отсюда всё остальное: раздел восстанавливается
из темы (`sections.section_of`), отдельного поля не нужно, а в поле «Раздел»
строки лежит один ключ — либо раздела, либо темы. Материалы, разложенные
до появления тем, продолжают работать без пересборки.

Сетка тем живёт в `subjects.py` (`SUBJECTS[subject]["sections"][*]["topics"]`),
57 тем на 8 разделов. **Коды совпадают с колонкой «Тема_код» базового контента
и с названиями вкладок теории** — это условие, а не совпадение: так вопросы
преподавателя и общие лежат в одной системе координат. Режим «По темам»
(`bot/handlers/topics.py`) строит свои `SECTIONS`/`SUBTOPICS` из этой же
сетки — второй копии списка быть не должно, расхождение молча оставит
теорию ненайденной. Закрыто тестом в `tests/test_topics.py`.

Свои темы преподавателя — ключи `6_c1`, `6_c2`, хранятся в `manifest.json`
в поле `topics` (плоская таблица на все разделы: ключ несёт раздел в себе).

**Порядок на экране: раздел → тема → файл.** Тема, как и раздел, привязана
к файлу целиком и залипает до конца сессии — пачку файлов в одну тему
не переспрашивают. «📚 Весь раздел, без темы» — законный выбор, а не отказ:
у полного билета по разделу тема не одна. У «Смешанных вопросов» шаг темы
пропускается: там вопросы разных разделов вперемешку.

**У ученика** внутри раздела показываются только непустые темы плюс «весь
раздел целиком». Выбор раздела вбирает и вопросы его тем (`_match_section`),
выбор темы — только её саму: `6_1` и `6_10` разные темы, и сверять их
вхождением строки нельзя.

## Жалобы на вопросы

Под каждым вопросом у ученика кнопка «⚠️ Что-то не так» и три причины
(`services/reports.py`). Причины делятся на две разные вещи, и это главное
здесь: **«нет вариантов» и «составлен некорректно» — заявка на поломку,
«не понял, о чём вопрос» — сигнал преподавателю объяснить.**

Отсюда правила:

- к порогу автоскрытия (`HIDE_THRESHOLD = 2`) считаются только жалобы
  на брак. Иначе из тренажёра исчезали бы самые сложные вопросы — те,
  что и надо разбирать, ведь на экзамене формулировка будет та же;
- вопрос прячется у пожаловавшегося только при браке. Непонятый остаётся
  в обороте;
- «Вернуть в тренажёр» ставит статус `confirmed`, и вопрос больше не
  скрывается автоматически — иначе следующие двое учеников убрали бы его
  снова, и так по кругу.

Хранение — в БД (`question_reports`, `question_flags`), не в файлах:
жалобы это события с привязкой к ученику. Ключ — тот же `question_hash`,
что у ответов и ошибок, поэтому пересборка `tests.json` и `/reparse`
жалоб не касаются.

Фильтрация — в `content_provider._drop_reported`, единственном месте, где
решается, кто что видит: все режимы подхватывают её сами.

Пропущенный по жалобе вопрос **не идёт в счёт результата** (`_calc_result`):
ученик на него не отвечал, засчитывать верным — врать в статистике.

**Общие вопросы базы живут по другому правилу** (решено 13.09.2026).
Преподаватель их не писал, поэтому ни скрывать, ни возвращать их не может:

- общий вопрос скрывается **у всех сразу**, когда на брак пожаловались
  ученики **двух разных преподавателей** (`BASE_HIDE_TEACHERS`). Двое
  друзей из одной группы базу не вычистят;
- решения хранятся отдельно, в `base_question_flags`, одни на всех;
  старые флаги преподавателя на общие вопросы игнорируются;
- карточка приходит **админу**, постоянная очередь — `/base_reports`
  (`bot/handlers/base_reports.py`): «вернуть в базу» ставит `confirmed`,
  и по жалобам вопрос больше не скрывается; «убрать навсегда» — `removed`;
- у преподавателя в «Спорных вопросах» только свои (`own_reports`).

Общий вопрос или свой — решает `content_provider.is_base_question`: текст
есть в базе и **нет** в файлах этого преподавателя. Вопрос, загруженный
преподавателем слово в слово как в базе, считается его. Google-таблицу
флаг не трогает; исправленный в таблице вопрос после `/update` вернётся
сам — у него другой текст, а значит другой отпечаток.

У преподавателя разбор идёт по одной карточке (`_reports_screen`), как
раскладка файлов по разделам. В карточке вопрос целиком с вариантами:
без них судить не о чем, а с ними «вариантов нет» перестаёт быть чужим
утверждением. Порядок: сначала скрытые, потом брак, в конце «не поняли».

## Форматы файлов

Принимаются `.docx` и **PDF с текстовым слоем**. Поддержка PDF — не второй
парсер, а только превращение файла в список строк: `ticket_parser.parse_lines`
разбирает строки, откуда бы они ни пришли. Заводить второй разбор нельзя —
любая правка чинилась бы дважды.

`services/pdf_tools.py` отличает документ от скана и **отказывает вслух**:

- букв меньше 40 на страницу → страницы это картинки, текста нет;
- больше 55% слов короче трёх букв → слой распознавания нечитаемый. Так
  выглядит скан, прогнанный распознавалкой с битой кодировкой: вместо
  «Прочитайте текст» извлекается «дяежи а ч а ожани». Принять такое молча
  нельзя — преподаватель увидит «0 вопросов» и не поймёт, при чём тут он.

Распознавания картинок нет: ни OCR, ни приёма фотографий. Это отдельная
работа, и главная сложность в ней не текст вопросов, а **ключ с ответами** —
ошибка распознавания там тихо испортит тренажёр.

Картинки вычищаются только из `.docx`: PDF кладётся как есть.

## Парсер билетов

Ядро — `services/ticket_parser.py`. `scripts/parse_tests.py` — тонкая обёртка
с CLI и выгрузкой в Google Sheets.

Два способа разбора: по абзацам с маркерами `А1.`, `В2.` (основной) и по
таблицам Word (запасной, для формата обобщений).

**Ключ с ответами ищется двумя путями.** Сначала по заголовку — «Ответы»,
«Ответы к тесту», «Правильные ответы», «Ключ», в том числе с ответами в той
же строке. Если заголовок назван непривычно («Эталоны», «Верные варианты»)
или его нет вовсе — по форме самой строки: `looks_like_answer_key` ищет
две и более пары «маркер — ответ» подряд.

Порог в две пары не случаен: одна пара встречается в тексте вопроса
(«задание А1 — самое простое»), и по одной паре ключом стал бы обычный
абзац, обрубив настоящий ключ ниже. Цена — билет с единственным вопросом
без заголовка не опознается, но таких билетов не бывает.

**Фильтр качества** (`validate`): в тренажёр попадает только целый вопрос —
есть текст, есть ответ, ответ не противоречит вариантам. Всё сомнительное
складывается в `manifest.json` с причиной. Один кривой вопрос бьёт по доверию
сильнее, чем отсутствие дюжины.

`PARSER_VERSION` пишется в манифест. **При изменении логики разбора поднимать.**

### Что здесь легко сломать

- **Ответы бывают трёх типов, и путать их нельзя**: многовыбор «135» (порядок
  не важен, сортируем), последовательность «БГВА» и соответствие «А2Б3В1Г4»
  (порядок важен), словесный ответ или год «Метрополия», «1795» (оставляем
  как есть). Раньше любые цифры считались многовыбором, и год 1795
  превращался в 1579.
- **Латиница в маркерах**: `Часть B: B1 — …` встречается наравне с кириллицей.
  Латинская `B` здесь всегда `В`, не `Б` — по начертанию.
- **Два формата ключа**: через точку с запятой и просто через пробел.
  Шаблон ограничивается следующим маркером, а не разделителем.
- **Ключ кончается там, где начинается обычный текст** (`key_block`).
  Иначе подпись под ключом его ломает: в строке «А2Б3В1 — соответствие»
  разбор видел пару «В1 — соответствие» и переписывал ей настоящий ответ.
  Перенос длинного ключа на следующую строку при этом сохраняется — такая
  строка начинается с середины ответа, но пар в ней много, а в подписи
  пара разве что случайная.
- **«Часть В:» — граница частей, а не вариант ответа.** Двоеточие после
  буквы не было учтено, и такая строка прилипала пятым вариантом
  к последнему вопросу части А.

Реальные образцы билетов лежат в `data/raw/tests/` (40 файлов) — на них надо
прогонять любые правки парсера. Из них только 6 содержат ключ с ответами;
остальные без ключа тренажёром стать не могут, и это не поломка парсера.

## Проверка ответа ученика

`services/llm.py:check_test_answer`. Порядок такой:

1. **Совпало с эталоном — отвечаем сами** (`answers_match`), модель не зовём.
2. Не совпало — разбирает модель: она объясняет ошибку и разбирает словесные
   ответы, где вариантов формулировки много.

Первый шаг появился 11.09.2026 после первого живого теста: преподаватель
выбрала «1 2 4», получила «❌ ты ошибся» — и в том же сообщении перечень
правильных: 1, 2, 4. Проверка целиком висела на `gpt-4.1-nano`, и она
ошиблась на точном совпадении строк. **Это худшая ошибка для доверия:**
после неё ученик не верит ни одной проверке.

`answers_match` умеет только досрочно сказать «верно». Всё, в чём она
не уверена, уходит модели — то есть работает как раньше, и засчитать
неверный ответ она не может по устройству.

Канонизация берётся у парсера (`ticket_parser.normalize_answer`): ответ
ученика и ответ из файла обязаны приводиться к одному виду одной и той же
логикой, иначе «124» и «1, 2, 4» окажутся разными ответами. Отсюда же
разбор типов — многовыбор сверяется множеством («142» = «124»), а год
только целиком: у 1453 и 1345 одни и те же цифры.

Побочно это чинит и расход: верный ответ больше не стоит обращения
к модели и приходит мгновенно.

## Объяснение ошибок

`services/answer_explainer.py`. Строится **от вопроса, вариантов и ответа
преподавателя**, без поиска по учебнику: работает на любом предмете, включая
те, где материалов нет вообще, и модель не может ошибиться в самом ответе.

Результат проверяется машинально: годы, века и имена собственные, которых нет
в вопросе или ответе, считаются приписанными — такое объяснение не
показывается. Сравнение по началу слова, чтобы склонения не давали ложных
срабатываний.

`rag/explainer.py:explain_error` (разбор по материалам через RAG) сейчас
никем не вызывается — оставлен на случай отдельной кнопки.

## Режимы

Видимые задаются в `SUBJECTS[subject]["modes"]`. Режимы `topics` (по темам)
и `mistakes` (мои ошибки) **работают, но спрятаны** на время прототипа —
они в `hidden_modes`. Вернуть в меню = перенести ключ в `modes`.
Меню собирается из конфига, хардкодить кнопки не надо.

### Две клавиатуры у преподавателя

`teacher_cabinet_kb` — настройка тренажёра (загрузка, состав, ученики).
`student_view_kb` — режимы занятий, у преподавателя с кнопкой «В кабинет».
Смешивать их нельзя: настройка и тренировка — разные задачи.

**Режим хранится самой клавиатурой**, а не на сервере: Telegram держит её
у пользователя до замены. Отсюда правило — не пересылать клавиатуру там,
где она не меняется, иначе преподавателя выбросит из режима ученика обратно
в кабинет посреди работы. Если ответ не меняет режим, `reply_markup`
не передавать вовсе.

## Форматирование вопросов (`bot/handlers/tests.py`)

Сырой текст → `_normalize_latin_markers()` (A→А, B→В) → `_clean_question_text()`
(срезает хвост «Ответ:») → для соответствий `_parse_and_reformat_correspondence()`
(буквенные пункты А–Е первыми, числовые после, многострочные схлопываются) →
для остальных вопросов части В разбивка по строкам регулярками.

Схема строки вопроса — та же, что в таблице тестов, менять нельзя:
`Вариант | Часть | № | Вопрос | Вар.1–5 | Ответ | Раздел`.

Реальный формат билета: `TICKET_PART_A = 16`, `TICKET_PART_B = 22`.

## Общий набор вопросов собран из двух листов

Базовый контент приехал двумя листами: обычные вопросы (1398) размечены
только разделами, а лист «Вопросы по темам» (2142) — темами, и наборы почти
не пересекаются. Второй ученику не показывался вовсе: его читал только режим
«По темам».

`sheets.topic_rows_as_tests` приводит второй набор к схеме строки тренажёра
(`Тема_код` → «Раздел», `Вар1` → «Вар.1», «Вариант» пустой — эти вопросы
не из билета), а `sheets_cache.base_tests_rows` отдаёт склейку. **Общий слой
читает только его** — прямое чтение `tests_rows` отдаёт половину набора
и теряет темы.

Отбрасываются: без темы, без текста, без ответа и совпадающие с обычным
набором. Склейка считается один раз на набор и пересчитывается, если набор
подменили.

Изоляции это не касается: чей контент показать, по-прежнему решает
`content_provider`, вопросы преподавателя с общими не смешиваются.

## Известные проблемы

- **`ADMIN_IDS` пуст** → проверка вида `if config.ADMIN_IDS and ...` пропускает
  всех, то есть `/reindex` может запустить любой пользователь, а это платно.
  При старте пишется предупреждение в лог.
- **Нет миграций БД** — см. выше.
- **Учительские FAISS-индексы не строятся**: 41 МБ на индекс при 2 МБ текста
  плюс деньги за эмбеддинги. Режим «Спросить» работает на общем индексе.
