# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Что это за проект

**AIda** — Telegram-бот, который превращает материалы преподавателя в тренажёр
для его учеников. Преподаватель загружает свои билеты в .docx, бот их разбирает
и собирает тренажёр; ученик приходит по приглашению и занимается на материалах
именно своего преподавателя.

Сделан на базе бота по истории Беларуси: каркас aiogram, RAG, движок тестов
и карточек переиспользованы. История осталась рабочим предметом и источником
базового контента.

Планы работ: `PLAN.md` (прототип по дням), `ROADMAP.md` (полная версия, подписка).

## Запуск и проверки

Локально проект работает в виртуальном окружении на **Python 3.12**
(на системном 3.14 нет готовых пакетов для FAISS):

```bash
.venv/Scripts/python.exe -m bot.main      # запуск бота
.venv/Scripts/python.exe -m pytest -q     # тесты
```

**Вывод в консоль Windows ломается на кириллице** (cp1251). Для любых команд
с русским выводом:

```bash
PYTHONIOENCODING=utf-8 ./.venv/Scripts/python.exe ...
```

На сервере (Linux, systemd) — юнит `historybot`, при переезде на AIda
переименовать:

```bash
sudo systemctl restart historybot
sudo journalctl -u historybot -f
```

Админские команды в Telegram: `/update` (перечитать Google Sheets),
`/reindex` (пересобрать FAISS), `/reparse` (перегнать все загруженные
преподавателями .docx текущей версией парсера).

## Архитектура

### Два уровня

**Предмет** задаёт «как работает»: какие режимы включены и откуда берётся
контент. Настраивается в `subjects.py`, в коде. Преподаватель это не трогает.

**Преподаватель** задаёт «на чём работает»: его билеты. Изоляция идёт по
`teacher_id` через пути на диске, а не через отдельных ботов или базы.

### Раскладка контента

Формат файлов одинаковый в обоих слоях, поэтому код читает контент по пути
и не знает, чей он:

```
data/
  subjects/{subject}/          базовый слой, общий для всех
      sheets_cache.json        снимок общих тестов и карточек
      theory_cache.json        теория по темам
  teachers/{tg_id}/{subject}/  контент преподавателя
      uploads/                 оригиналы .docx без картинок
      tests.json               результат разбора
      manifest.json            что, когда, сколько, версия парсера
  vectorstore/                 общий FAISS-индекс по учебнику истории
```

Пути строит `services/storage.py` — не собирать их вручную в хендлерах.

### Кто какой контент видит

`services/content_provider.py` — **единственное** место, где решается этот
вопрос. Хендлеры запрашивают набор по `telegram_id` и не знают о слоях.
Политика берётся из `SUBJECTS[subject]["sources"]`:

| Режим | Политика | Куда растёт |
|---|---|---|
| tests | `teacher` | teacher + добор из базы |
| flashcards | `base` | base + teacher |
| ask | `base` | base + teacher |

Включить смешивание — правка конфига, не переписывание режимов.

**Ключевой инвариант: ученик видит вопросы только своего преподавателя.**
Ломать нельзя, покрыто тестами в `tests/test_content_provider.py`.

Преподаватель получает собственный контент (`resolve_teacher_id` возвращает
его самого) — поэтому режим «пройти свой тренажёр» работает без отдельной
ветки кода.

### Данные при старте

`bot/main.py` → `.env` → `init_db()` → снимок Sheets с диска (если есть —
в Google не ходим) → теория с диска → FAISS-индекс (если папка на месте,
пересборка пропускается) → роутеры → polling.

## Роли и онбординг

`/start` → выбор роли → выбор предмета → дальше по-разному:

- **преподаватель**: сразу создаются папки и код приглашения, анкету не спрашиваем;
- **ученик**: имя и класс, привязка к преподавателю по коду.

Схема БД (`database/db.py`, SQLite): `users` (роль, `teacher_id`,
`current_subject`), `teachers` (код приглашения), `teacher_content`,
`mistakes`, `completed_topics`.

**Миграций нет** — только `CREATE TABLE IF NOT EXISTS`. При изменении схемы
на живой базе это надо решать отдельно.

## Загрузка билетов преподавателем

`bot/handlers/teacher_upload.py` → `services/teacher_content.py`.

1. Приём .docx (лимит 20 МБ — больше Telegram боту не отдаёт).
2. `services/docx_tools.py:strip_media` — картинки заменяются заглушкой 1×1.
   В реальных билетах это 94% веса, а парсеру они не нужны. Связи внутри
   документа остаются целыми, разбор после чистки идентичен.
3. Оригинал кладётся в `uploads/` и **никогда не удаляется** — чтобы новую
   версию парсера можно было прогнать по всему накопленному без просьб
   к преподавателям перезаливать.
4. `tests.json` **всегда пересобирается из `uploads/` целиком**, а не
   дописывается. Поэтому повторная загрузка файла с тем же именем заменяет
   его вопросы, а не двоит.

## Разделы преподавателя

Сетка разделов программы живёт в `subjects.py` (`SUBJECTS[subject]["sections"]`)
— ключи те же, что в поле `Раздел` базового контента, поэтому вопросы
преподавателя и общие лежат в одной системе координат. Свои разделы
преподаватель добавляет сам, они получают ключи `c1`, `c2` и хранятся
в его манифесте.

**Раздел привязан к файлу целиком, а не к отдельному вопросу.** Привязка
лежит в `manifest.json` (`files[].section`), а не в строках `tests.json`:
строки пересобираются из `uploads/` при каждой загрузке и при `/reparse`,
и раскладка бы стиралась. `rebuild()` читает прежний манифест и подставляет
раздел в строки заново — покрыто `tests/test_sections.py`.

Логика без диска и бота — `services/sections.py`: список разделов, названия
и подсказка по имени файла (годы, римские века, ключевые слова). При ничьей
подсказка молчит: подтверждённая не глядя, она портит материалы тише,
чем лишний вопрос.

Порядок на экране: файл можно прислать в любой момент, бот разбирает его
и спрашивает раздел; выбранный раздел держится до конца сессии, поэтому
пачку файлов не переспрашивают. Кнопка кабинета ведёт в мастер «сначала
раздел, потом файл». Старые загрузки разбираются из «Мой тренажёр» →
«Разделы» → «Разложить».

**У ученика** список разделов строится из его собственного набора вопросов
(`_available_sections` в `bot/handlers/tests.py`): показываются только
непустые разделы, включая свои разделы преподавателя. Вопросы без раздела
собраны в псевдораздел **«🔀 Смешанные вопросы»** — это полные билеты, где
разделы перемешаны: приписать им один нельзя, а тренироваться на них нужно.
Ключ псевдораздела — `UNSORTED_KEY`, внутри превращается в пустой ключ.

Название одно на обе стороны (`sections.UNSORTED_TITLE`): преподаватель
кладёт файл в «Смешанные вопросы» и там же его находит ученик. Название
говорит о составе, а не о происхождении файла: «Пока без раздела» читалось
как «решу потом», «Готовые варианты» — как источник, а важно ровно то,
что внутри вопросы из разных разделов.

**Темы — второй уровень, ещё не сделан.** Формат тот же: ключ вида `6.2`
в том же поле. Экраны от этого не меняются, добавится один шаг выбора.

## Жалобы на вопросы

Под каждым вопросом у ученика кнопка «⚠️ Что-то не так» и три причины
(`services/reports.py`). Причины делятся на две разные вещи, и это главное
здесь: **«нет вариантов» и «составлен некорректно» — заявка на поломку,
«не понял, о чём вопрос» — сигнал преподавателю объяснить.**

Отсюда правила:

- к порогу автоскрытия (`HIDE_THRESHOLD = 2`) считаются только жалобы
  на брак. Иначе из тренажёра исчезали бы самые сложные вопросы — те,
  что и надо разбирать, ведь на экзамене формулировка будет та же;
- вопрос прячется у пожаловавшегося только при браке. Непонятый остаётся
  в обороте;
- «Вернуть в тренажёр» ставит статус `confirmed`, и вопрос больше не
  скрывается автоматически — иначе следующие двое учеников убрали бы его
  снова, и так по кругу.

Хранение — в БД (`question_reports`, `question_flags`), не в файлах:
жалобы это события с привязкой к ученику. Ключ — тот же `question_hash`,
что у ответов и ошибок, поэтому пересборка `tests.json` и `/reparse`
жалоб не касаются.

Фильтрация — в `content_provider._drop_reported`, единственном месте, где
решается, кто что видит: все режимы подхватывают её сами.

Пропущенный по жалобе вопрос **не идёт в счёт результата** (`_calc_result`):
ученик на него не отвечал, засчитывать верным — врать в статистике.

У преподавателя разбор идёт по одной карточке (`_reports_screen`), как
раскладка файлов по разделам. В карточке вопрос целиком с вариантами:
без них судить не о чем, а с ними «вариантов нет» перестаёт быть чужим
утверждением. Порядок: сначала скрытые, потом брак, в конце «не поняли».

## Парсер билетов

Ядро — `services/ticket_parser.py`. `scripts/parse_tests.py` — тонкая обёртка
с CLI и выгрузкой в Google Sheets.

Два способа разбора: по абзацам с маркерами `А1.`, `В2.` (основной) и по
таблицам Word (запасной, для формата обобщений). Ключ с ответами ищется после
заголовка «Ответы».

**Фильтр качества** (`validate`): в тренажёр попадает только целый вопрос —
есть текст, есть ответ, ответ не противоречит вариантам. Всё сомнительное
складывается в `manifest.json` с причиной. Один кривой вопрос бьёт по доверию
сильнее, чем отсутствие дюжины.

`PARSER_VERSION` пишется в манифест. **При изменении логики разбора поднимать.**

### Что здесь легко сломать

- **Ответы бывают трёх типов, и путать их нельзя**: многовыбор «135» (порядок
  не важен, сортируем), последовательность «БГВА» и соответствие «А2Б3В1Г4»
  (порядок важен), словесный ответ или год «Метрополия», «1795» (оставляем
  как есть). Раньше любые цифры считались многовыбором, и год 1795
  превращался в 1579.
- **Латиница в маркерах**: `Часть B: B1 — …` встречается наравне с кириллицей.
  Латинская `B` здесь всегда `В`, не `Б` — по начертанию.
- **Два формата ключа**: через точку с запятой и просто через пробел.
  Шаблон ограничивается следующим маркером, а не разделителем.

Реальные образцы билетов лежат в `data/raw/tests/` (40 файлов) — на них надо
прогонять любые правки парсера. Из них только 6 содержат ключ с ответами;
остальные без ключа тренажёром стать не могут, и это не поломка парсера.

## Объяснение ошибок

`services/answer_explainer.py`. Строится **от вопроса, вариантов и ответа
преподавателя**, без поиска по учебнику: работает на любом предмете, включая
те, где материалов нет вообще, и модель не может ошибиться в самом ответе.

Результат проверяется машинально: годы, века и имена собственные, которых нет
в вопросе или ответе, считаются приписанными — такое объяснение не
показывается. Сравнение по началу слова, чтобы склонения не давали ложных
срабатываний.

`rag/explainer.py:explain_error` (разбор по материалам через RAG) сейчас
никем не вызывается — оставлен на случай отдельной кнопки.

## Режимы

Видимые задаются в `SUBJECTS[subject]["modes"]`. Режимы `topics` (по темам)
и `mistakes` (мои ошибки) **работают, но спрятаны** на время прототипа —
они в `hidden_modes`. Вернуть в меню = перенести ключ в `modes`.
Меню собирается из конфига, хардкодить кнопки не надо.

### Две клавиатуры у преподавателя

`teacher_cabinet_kb` — настройка тренажёра (загрузка, состав, ученики).
`student_view_kb` — режимы занятий, у преподавателя с кнопкой «В кабинет».
Смешивать их нельзя: настройка и тренировка — разные задачи.

**Режим хранится самой клавиатурой**, а не на сервере: Telegram держит её
у пользователя до замены. Отсюда правило — не пересылать клавиатуру там,
где она не меняется, иначе преподавателя выбросит из режима ученика обратно
в кабинет посреди работы. Если ответ не меняет режим, `reply_markup`
не передавать вовсе.

## Форматирование вопросов (`bot/handlers/tests.py`)

Сырой текст → `_normalize_latin_markers()` (A→А, B→В) → `_clean_question_text()`
(срезает хвост «Ответ:») → для соответствий `_parse_and_reformat_correspondence()`
(буквенные пункты А–Е первыми, числовые после, многострочные схлопываются) →
для остальных вопросов части В разбивка по строкам регулярками.

Схема строки вопроса — та же, что в таблице тестов, менять нельзя:
`Вариант | Часть | № | Вопрос | Вар.1–5 | Ответ | Раздел`.

Реальный формат билета: `TICKET_PART_A = 16`, `TICKET_PART_B = 22`.

## Колонки Google Sheets (базовый контент)

- Тесты: `Вопрос`, `Ответ`, `Вар.1`–`Вар.5`, `Раздел`, `Вариант`
- Даты: `Дата`, `Событие`, `Раздел`
- Понятия: `Понятие`, `Определение`, `Раздел`
- Личности: `Личность`, `Роль в истории`, `Раздел`

## Переменные окружения

| Переменная | Назначение |
|---|---|
| `TELEGRAM_TOKEN` | токен бота |
| `OPENAI_API_KEY` | ключ OpenAI |
| `LLM_MODEL` | основная модель (по умолчанию `gpt-4.1`) — чат и RAG |
| `LLM_MODEL_MINI` | быстрая модель — проверка ответов, объяснения |
| `TEXTBOOK_DOC_ID`, `NOTES_DOC_ID`, `THEORY_DOC_ID` | Google Docs с материалами |
| `TESTS_SHEET_ID`, `FLASHCARDS_SHEET_ID` | таблицы базового контента |
| `VECTORSTORE_PATH` | путь к FAISS-индексу |
| `HISTORY_CT_DB_PATH` | путь к SQLite |
| `ADMIN_IDS` | Telegram ID админов через запятую |

Не используются, остались от прежних решений: `COHERE_API_KEY`,
`RERANK_MODEL`, `RERANK_TOP_N` (реранк отключён, `rerank_docs` возвращает
документы как есть), `CHROMA_COLLECTION_NAME` (перешли на FAISS).

## Известные проблемы

- **`ADMIN_IDS` пуст** → проверка вида `if config.ADMIN_IDS and ...` пропускает
  всех, то есть `/reindex` может запустить любой пользователь, а это платно.
  При старте пишется предупреждение в лог.
- **`MemoryStorage`** → перезапуск бота обрывает всем незаконченные тесты
  и карточки.
- **Нет миграций БД** — см. выше.
- **Учительские FAISS-индексы не строятся**: 41 МБ на индекс при 2 МБ текста
  плюс деньги за эмбеддинги. Режим «Спросить» работает на общем индексе.
